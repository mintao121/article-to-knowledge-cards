## 知识卡片（共 7 张）

### 卡片 1：缓存用来给慢源头“减负”
- **核心知识**：缓存把频繁访问的数据放在更快的存储上，从而减少对数据库等慢速源头的访问。
- **简明解释**：数据库通常比内存慢很多。把热点数据临时放在快的地方，下次直接取，整体就快了。
- **例子**：把商品详情放 Redis，用户反复查看时不再每次查数据库。
- **自测问题**：为什么说“频繁访问的数据”才适合放缓存？冷数据放缓存会怎样？

### 卡片 2：命中与未命中决定要不要回源
- **核心知识**：缓存命中（hit）是数据在缓存中找到；未命中（miss）是没找到，需要回源去取。
- **简明解释**：hit 走快路，miss 要走慢路并通常顺手把结果补回缓存，两套路径性能差很多。
- **例子**：查用户信息命中缓存 1ms 返回；未命中则查库 20ms 再回填。
- **自测问题**：为什么 miss 时除了回源，还常常要把结果写回缓存？

### 卡片 3：失效策略决定缓存何时更新
- **核心知识**：缓存必须规定“什么时候失效/更新”，常见做法是 TTL（到点过期）和 LRU（最近最少用优先淘汰）。
- **简明解释**：缓存不能永远有效，否则会一直返回旧数据；TTL 按时间过期，LRU 按使用频率淘汰。
- **例子**：TTL 设 60 秒，过期的商品库存会自动重新读取；LRU 在内存满时先扔掉最久没用的条目。
- **自测问题**：TTL 和 LRU 分别按什么规则决定一条缓存该不该被丢掉？

### 卡片 4：一致性是缓存与源数据的同步问题
- **核心知识**：缓存与源数据可能不同步，一致性指两者是否保持一致。
- **简明解释**：源数据改了但缓存没更新，读到的就是旧值；这是用缓存必须面对的代价。
- **例子**：改了商品价格，缓存里还是旧价，用户看到错误金额。
- **自测问题**：为什么“先更新数据库还是先删缓存”会成为缓存设计的经典难题？

### 卡片 5：击穿与雪崩会压垮源库
- **核心知识**：大量 key 同时失效或热点 key 被打穿，会让请求瞬间全压到源库，造成击穿/雪崩。
- **简明解释**：缓存本是“ shield”，一旦集体失效，源库直接裸奔，可能被打挂。
- **例子**：凌晨大批缓存 TTL 同时到点，秒杀开始时数据库瞬间被打满。
- **自测问题**：给缓存过期时间加随机抖动，能缓解上面哪种问题？

### 卡片 6：缓存的核心收益是降延迟、提吞吐
- **核心知识**：缓存能显著降低响应延迟、提升系统吞吐。
- **简明解释**：少访问慢源头 = 更快返回 + 能扛更多请求。
- **例子**：读多写少的榜单接口加缓存后，QPS 从 2k 升到 20k。
- **自测问题**：什么类型的业务（读多写少 vs 写多读少）最能从缓存受益？

### 卡片 7：缓存的代价是数据可能不一致
- **核心知识**：缓存带来性能收益，但引入数据不一致风险，需要按业务权衡。
- **简明解释**：没有“又快又永远准”的免费午餐，钱相关场景对一致性要求高，要慎用或强一致。
- **例子**：余额、库存类数据缓存要格外小心，常配合主动失效或短 TTL。
- **自测问题**：为什么“余额”比“点赞数”更不适合用长 TTL 缓存？
